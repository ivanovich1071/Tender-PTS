

### **Пошаговый алгоритм создания MVP сервиса автоматизации тендеров**

Общая философия: Мы создаем не идеальный продукт, а инструмент для проверки гипотезы. Наша главная гипотеза: компании готовы платить за автоматизацию рутинного мониторинга тендеров и заведения сделок в Битрикс24. Каждый шаг должен приближать нас к подтверждению или опровержению этой гипотезы с минимальными затратами.

### **Этап 1: Прототипирование и проектирование (Недели 2-4)**

#### **Шаг 1.1: Проектирование архитектуры**

Цель: Разработать высокоуровневую схему, которая определяет, как все компоненты системы будут взаимодействовать друг с другом, обеспечивая надежность, масштабируемость и безопасность.

Результат: Схема архитектуры и текстовое описание.

2\. Текстовое описание архитектуры:

a) Поток данных от площадок к серверу:

* Источники данных: B2B-Center API, Zakupki360 API.  
* Метод получения данных: Для MVP используется механизм периодического опроса (polling) API площадок по расписанию (например, каждые 30 минут). В будущем для B2B-Center можно рассмотреть вариант получения данных по webhook, если партнерская программа это предусматривает.  
* Процесс:  
  1. Веб-приложение (на основе Django/FastAPI) формирует задание на сбор данных (например, "запросить все тендеры за последние 30 минут по ключевым словам пользователя").  
  2. Задание помещается в очередь задач (Redis Queue или Celery).  
  3. Отдельный процесс (Worker) берет задание из очереди.  
  4. Worker делает запрос к API площадки (B2B или Zakupki360), соблюдая лимиты запросов (Rate Limiting). Данные кэшируются, чтобы не делать повторные запросы для одинаковых задач от разных пользователей.  
  5. Полученные сырые данные (JSON) записываются в базу данных (PostgreSQL) в таблицу `raw_tenders` для аудита и повторной обработки.  
  6. Данные парсятся и проходят первичную фильтрацию по общим правилам (например, отсеиваются нерелевантные регионы).  
  7. Результаты фильтрации сохраняются в основную таблицу `tenders`.

b) Взаимодействие с API Битрикс24:

* Метод интеграции: REST API Битрикс24.  
* Процесс:  
  1. Для каждого тендера, прошедшего фильтрацию, в очередь задач добавляется задание на создание сделки.  
  2. Специализированный Worker берет задание из очереди.  
  3. Worker использует OAuth 2.0 токен пользователя для доступа к его Bitrix24.  
  4. Выполняется API-запрос `crm.deal.add` с заполнением полей:  
     * `TITLE`: Название тендера \+ номер.  
     * `OPPORTUNITY`: Бюджет тендера (если есть).  
     * `DATE_CLOSED`: Дата окончания подачи заявок.  
     * `COMMENTS`: Ссылка на тендер, краткое описание.  
     * Привязка к контакту/компании (если найдены в CRM по ИНН/названию заказчика).  
  5. Результат работы (успех или ошибка) логируется в базу данных в таблицу `tasks_log`.

c) Хранение данных пользователей:

* База данных (PostgreSQL):  
  * `Таблица users`: Профили пользователей (email, хэш пароля, настройки часового пояса).  
  * `Таблица user_settings`: Настройки интеграции с Bitrix24 (OAuth токены, ID воронки сделок), ключевые слова для фильтрации, прочие предпочтения.  
  * `Таблица tenders`: Отфильтрованные тендеры с привязкой к пользователю, который их получил.  
  * `Таблица tasks_log`: Лог всех выполненных фоновых задач (для отладки и уведомления пользователя об ошибках).  
* Кэш (Redis):  
  * Ключи сессий пользователей.  
  * Временные данные API-запросов для избежания лишних вызовов.  
  * Очередь задач (Redis Queue).

#### **Шаг 1.3: Техническое задание (ТЗ) для разработки**

Цель: Создать документ, который однозначно трактуется разработчиками и содержит исчерпывающее описание функционала для реализации на этапе разработки ядра MVP.

Формат: Пользовательские истории (User Stories).

---

User Stories для разработчиков:

1\. Интеграция с внешними API

* Как система, я хочу иметь модули для работы с API B2B-Center и Zakupki360, чтобы получать актуальные данные о тендерах.  
  * Критерии готовности (Acceptance Criteria):  
    * Реализованы отдельные классы/модули для каждого API.  
    * Обработаны основные HTTP ошибки (4xx, 5xx).  
    * Реализован механизм повторного запроса с экспоненциальной задержкой (exponential backoff) при ошибках 429 (Too Many Requests).  
    * Конфигурация (API-ключи, URL endpoints) вынесена в настройки приложения.

2\. Аутентификация и авторизация пользователя

* Как пользователь, я хочу зарегистрироваться и войти в систему по email и паролю, чтобы получить доступ к своему аккаунту.  
  * Критерии готовности:  
    * Реализованы endpoints `/api/auth/register`, `/api/auth/login`.  
    * Пароли хранятся в виде хэшей (bcrypt).  
    * Сессия пользователя поддерживается via JWT-токен или session cookie.  
    * На фронтенде есть соответствующие формы.

3\. Управление настройками интеграции с Bitrix24

* Как пользователь, я хочу указать данные для подключения к моему Bitrix24 (домен, OAuth-токен), чтобы система могла создавать сделки.  
  * Критерии готовности:  
    * В интерфейсе есть раздел "Настройки интеграции".  
    * Реализован OAuth 2.0 flow для получения токена (или инструкция, как его получить).  
    * Токен безопасно хранится в базе данных (зашифрован).  
    * Реализована проверка валидности токена при сохранении.

4\. Управление ключевыми словами для фильтрации

* Как пользователь, я хочу добавлять, редактировать и удалять ключевые слова/теги, чтобы система искала тендеры, соответствующие моей специализации.  
  * Критерии готовности:  
    * В интерфейсе есть интерфейс CRUD (Create, Read, Update, Delete) для управления списком слов.  
    * Слова сохраняются в базе данных в таблице `user_settings`.

5\. Запуск мониторинга и получение тендеров

* Как пользователь, я хочу нажать кнопку "Запустить поиск" или чтобы поиск запускался автоматически по расписанию, чтобы получить в свой личный кабинет список подобранных тендеров.  
  * Критерии готовности:  
    * Реализована фоновая задача (worker), которая по расписанию опрашивает API.  
    * Фильтрация по ключевым словам пользователя происходит после получения сырых данных.  
    * Результаты сохраняются в базу с привязкой к пользователю.  
    * Пользователь видит список в интерфейсе с пагинацией.

6\. Создание сделки в Bitrix24

* Как система, я хочу автоматически создавать сделку в Bitrix24 для каждого подходящего тендера, чтобы пользователь видел ее в своей CRM.  
  * Критерии готовности:  
    * Реализован worker, который слушает очередь задач на создание сделок.  
    * Для создания сделки используется метод Bitrix24 REST API `crm.deal.add`.  
    * Заполняются обязательные и дополнительные поля сделки на основе данных о тендере.  
    * Ошибки (невалидный токен, недоступность CRM) логируются и отображаются пользователю в интерфейсе.

7\. Просмотр лога действий

* Как пользователь, я хочу видеть историю действий системы (когда был запуск, сколько тендеров найдено, какие ошибки возникли), чтобы контролировать процесс.  
  * Критерии готовности:  
    * В интерфейсе есть вкладка "История" или "Лог".  
    * Данные берутся из таблицы `tasks_log`.  
    * Отображается статус каждой задачи (успех, ошибка), время и описание.
